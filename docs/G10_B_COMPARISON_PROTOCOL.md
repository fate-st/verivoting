**这是比较设计，不是已完成的系统性能实验。** 本轮仅完成G10-A干净30轮复现，没有新增G10-B接收器、证明生成或链上交易。

## 1. 固定什么、不比较什么

复用D5/W32、三候选人、原D2池indices0..7、两个连续B4、原25字段单票输入/选票VK、原B4状态VK、原SnarkPack V2/SRS，
以及完全相同的election/context/注册根/接受根计划/CT0、CT1、CT2。根和各来源哈希均在机器清单中。
该清单不是新的密码学Manifest，不换曲线、哈希、PRF、Merkle编码或安全假设。

四条原生路线是**本项目内的受控基线**，不是Helios/Belenios等完整系统的性能复刻；不能把名字Legacy解释为代表所有传统投票方案。
G8第五条是本地Prague备用路线，既不是精确SnarkPack EVM，也不是公链运行。

## 2. 两个比较面板，禁止混合单位/工作量

### A：原生接收阶段（下一项可实现的最小目标）

| 路线 | 真正执行的动作 | 当前状态 |
| --- | --- | --- |
| Legacy individual | 八次逐票Groth16验证、逐票直接累计、逐票checkpoint写入 | 新匹配接收实现未完成 |
| Transaction-batch | 两次B4接收，各四次逐票Groth16，直接累计并一次原子写入 | 新匹配接收实现未完成 |
| SnarkPack + Direct Fold | 两次B4聚合验证及完整记录/状态/NF检查、直接累计 | 当前G10-A已测，需在新四路线入口内一起重测 |
| SnarkPack + State Proof | 相同B4聚合和共同检查，验证两份状态证明 | 当前G10-A已测，需在新四路线入口内一起重测 |

共同终点必须是相同CT2、8个已用NF及无漏计/重复计票。原生接收计时不含DKG证书验签、私密传输、P3或Winner写入。
当前G10-A使用固定fixture给出的信任锚和accepted roots；这不是在线独立登记机构的认证实验，也不证明接收前防审查。
源码内真实调用相应验证器和群运算，不能把八次验证组件时间加上一个历史fold时间称为完整Legacy路线。

### B：完整生命周期（后续）

各候选路线还必须接入同一初始化/证书认证、冻结、Trustee承诺/私密份额验证、门限解密与有界解码、结果证明/发布后缀。
只比较相同工作量和相同执行环境。G8已有收据覆盖这一更大范围，不能拿其Gas与面板A的毫秒作同范围排名。
也不能把G8历史费用加到新原生接收时间上构成“完整系统测量”。

## 3. Legacy与批次接收的共同认证契约

两个新逐票基线必须针对同一预先确定的有序接受记录，而不只是验证任意八张有效选票：

1. 冻结同一两个B4记录根和位置0..7；逐票接收要验证其确属对应已接受根/位置，批次接收要验证同一完整有序根。
2. 逐票模式不能直接套用B4 Receiver再改名。它必须执行八次实际状态更新，并在第4/8票后分别达到CT1/CT2。
3. 单票记录/25字段/原证明严格对应，同一注册根、key/context、公钥及candidate顺序不能由调用者替换。
4. 所有模式检查鲜活NF、正确旧状态和规定顺序，失败不留下部分写入。逐票写入和B4原子写入的区别要明确计入成本。
5. 共同接受根/记录认证成本不能只从某一条路线移出计时；若逐票用Merkle路径，其路径计算/验证/通信必须记账，不能默认为免费。

这些是基线可比性的必要条件，不是新增故障/攻击矩阵。没有匹配实现以前，两个逐票基线的完整耗时保持null。
新四路线入口准备好后固定新源码提交，在同一二进制/同一环境下交替测量四路线；不能将本轮两个数据点与未来两条新实现拼成一轮四路线实验。
优先只做现有两批B4，不先扩B64、B128、B256。

## 4. 生成成本、通信和内存必须独立记账

- Ballot Setup、State Setup和P3 Setup作为离线阶段单列，不能混入在线验证，也不能遗漏可信设置限制。
- 选票Prove、Aggregation、State Prove、P3 Prove分别用真实执行记录。同一选票的共同生成成本在每条适用路线中按一致规则计入；没有状态证明的路线不能被加上该证明者负担。
- 本轮全部复用，生成次数0不表示生成时间0；当前比较时间保持null/REUSED_NOT_RETIMED。
- 机器清单保存G2-D/G2-E/G6历史生成时间及JSON哈希，表明这些成本确实存在。但它们不是本轮匹配的生成测量，不求和冒充本轮端到端结果。
- 完整比较中Setup选择次数、证明样本数、内存/时间预算须先固定；不能为扩大统计量无界重做大电路Setup/Prove。
- 内存分别测验证者与证明者、各路线独立进程。当前G10-A共享进程RSS不是逐路线比较，也不能替代约数GiB的历史State/P3 Prove峰值。
- 单独报告proof、matrix、接受记录/根/路径、CT和认证材料；派生37项输入若已在矩阵/CT中，不重复相加。明确是二进制分项、完整封包还是calldata。

G8已有同一次执行的成功17笔65,473,608 Gas（含部署）和业务31,390,919 Gas仅作来源带哈希的历史参考。
部署、成功业务、失败验收、calldata、签名交易字节分别列出；证明/矩阵已在calldata内，不重复相加。
没有新匹配链上实现时，精确SnarkPack路线Gas保持null，不能把它写成0或从原生时间推算。

## 5. Direct Fold与Full Tally两个消融

Direct Fold是有效的正确性基线，不是不安全方案。当它检查相同已接受记录并实际重算所有累计分量时，与State Proof应满足相同状态正确性要求。
State Proof的价值应由计算外包/验证负担/部署和数据可用性条件及额外证明成本回答，不能预设只有它能防遗漏，或预设它一定降低Gas。
当前G10-A数据反而显示State路线原生接收更慢，结论必须保留。

Full Tally vs Winner-only必须另开独立实验：同一CT2、DKG及合法Trustee份额，分别执行完整公开计票与仅公布Winner的规则。
两个发布分支要隔离归档；Full Tally的可用份额、opening和完整票数不能混入Winner-only公共fixture。
若公开合集同时含同一目标的Full Tally，就已公开该票数，不能用这个合集证明Winner-only计票隐藏。
比较公开字节/证明时间/Gas不替代T4联合提取或T5 Function-Equal证明。
